# Testing — Bra Auto Measure

The suites answer four different questions: **does it build**, **does it run**,
**is it correct**, and **did it change**. Knowing which question a suite answers
tells you when to run it. All commands are `npm run <name>` and live in
`scripts/`.

---

## Quick guide: what to run when

- **After any `src/` edit:** `build` → `check` → `smoke`.
- **After a detection / anchor change:** add `invariants`, `contract`, and
  `golden` (re-baseline with `golden --update` only when the change is
  intentionally better, confirmed by `accuracy`).
- **After a learning / meaning / evidence change:** the matching subsystem suite.
- **Before shipping:** the full set.

`check`, `pipeline-tests`, `junction-tests`, and `export-hidden` need no browser.
The rest drive a headless Chrome over raw CDP (zero npm deps); `accuracy`
additionally needs labelled ground truth and a local Chrome install.

## The suites

| Command | Question it answers | What it does | Runner |
|---|---|---|---|
| `check` | Does it build & wire? | Asserts the committed `app.js` matches what `src/` would build (read-only freshness gate), parse-validates every `src/` part in isolation plus the standalone `opencv_*` / `potrace` / script files, checks every `src/**/*.js` is registered in `source-parts.mjs`, validates the rule JSON contract, and runs the two **shared-scope** gates: no name declared at top level in two parts (the later one silently wins for every caller), and no load-time read of a `const`/`let`/`class` declared in a later part (those do not hoist, so it throws a TDZ `ReferenceError`). | Node, parse-only |
| `smoke` | Does it run end to end? | Headless Auto Mode run on `demo/demo1.jpg`; asserts the pipeline completes and the output is structurally sound. | Chrome CDP |
| `golden` | **Did output change?** (stability) | Runs detection on **every** `demo/*.jpg` and diffs anchors (by kind), draft count, per-POM **draft-line geometry** (start/end/control points, normalized to the source image — guards the fixture→draft path that anchor drift can't see), and `detection.quality` against committed per-image baselines. Fails on drift. `--update` re-seeds baselines; `GOLDEN_TOL` overrides tolerance. | Chrome CDP |
| `accuracy` | **Is it correct?** | Scores detector seeds against **human-placed TD ground truth** in `scripts/groundtruth/`. Lower is better. Bands: tight ≈0.02 ("a TD wouldn't touch it"), loose ≈0.04 ("a nudge fixes it"), normalized image units. Pins the deterministic offline detector for reproducibility. **Regression gate:** every full run is also compared against the committed `scripts/groundtruth/accuracy-baseline.json`; if any labeled image's mean/max error, any anchor kind's mean error, the overall mean, or the count of unseeded ground-truth anchors gets worse (beyond small epsilons — `ACCURACY_GATE_MEAN_EPS`/`_MAX_EPS`/`_KIND_EPS`), the suite exits non-zero. Improvements pass; ratchet them in with `accuracy --update`. **Stale-read guard:** Chrome's cache is disabled and, before every detection, the served `app.js` is SHA-256-verified against disk (re-navigates until fresh) — on this Drive checkout the first read after file churn can silently serve an old build, which shows up as the fragile cradle anchors going missing; images whose ground-truth anchors still go unseeded are re-detected once more. `--only` skips the gate (partial corpus). **Multi-photo boards:** a ground-truth file may name its own image with `imagePath` (so boards in a `demo/` subfolder are discovered at all — the directory scan is not recursive) and declare a `board.aux` list, which is loaded as extra board photos so the TD's real two-photo board is reproduced instead of the primary alone. Single-image fixtures are unaffected. | Chrome CDP + ground truth |
| `measurement-accuracy` | **Are the measured POM *values* correct?** | Value-level mirror of `accuracy` (which scores anchor *positions*). Scores each POM's measured value (inches) against per-POM TD ground truth in `scripts/groundtruth/measurements/<image>.json`, with the same one-sided gate vs `scripts/groundtruth/measurement-accuracy-baseline.json` (epsilons `MEASURE_GATE_MEAN_EPS`/`_MAX_EPS`/`_POM_EPS`). **Non-blocking until Mode B ships:** only `source: td_confirmed` GT is gated (`draft_pending_td` is report-only), and scoring needs a measured-value source (`--measured <file>`) that Stage 1 wires from the measurement engine. Prove the gate math offline with `measurement-accuracy-selftest`. Part of US-039 (Mode B Stage 0). **Roll-out (US-041):** `measurement-accuracy --measured=<run> --promote` recommends the per-POM `MODE_B_ENABLED_POMS` set (only td_confirmed POMs whose fused value beats library-only); `mode-b-readiness` prints, with no ground truth, which POMs produce a coherent measured value across the demo fixtures (where to label GT first). | Node |
| `invariants` | Are structural properties intact? | Checks properties that must hold with no ground truth: geometry (A1–A6), cup bounds (B1–B4), visibility (D1–D3) and shared rows (E1–E4), across all demos. **E1–E3** guard the row model behind the force-levelled horizontal spans: `band-left`/`band-right`, `chest-left`/`chest-right` and `back-strap-left`/`back-strap-right` are each the two ends of ONE row, so they must share a `y` exactly — POM 1 / 3 / 15 draw level at the LEFT end's `y` and silently miss the right pin by any gap. **E4** ties POM 16's drawability to the apex pair's slant: the detector repairs a straddled pair by re-searching the outlier side (US-084) and the drafter demotes past the same 0.06 limit (US-083), so the two numbers live in two files and E4 is what catches them drifting apart. Complements `golden` (change) and `accuracy` (correctness). | Chrome CDP |
| `contract` | Are the fragile POMs semantically right? | Semantic checks (aligned to the POM contract in `POMS_CONTRACT.md`) for the 6 hard front-view POMs — 6, 7, 8 (cradle/cup heights), 9, 10 (inner cup), 16 (apex) — on every demo. Also carries four cross-cutting series: **CLA** (each drafted endpoint sits on its anchor, recomputing the drafter's own formula), **HLN** (the horizontal spans are drawn level), **TRA** (POM 1 / 3 / 15's line passes within `EPS_LINE_ANCHOR` of BOTH required anchors — the property CLA cannot check, because for a force-levelled span CLA reproduces the very `y`-discard that can throw the line off its right-hand pin), **RPF**, and **APX**. **RPF** re-seeds anchors from the captured detection with one side's band/chest ink fields nulled: every fixture in the corpus detects ink on BOTH sides, so the one-sided seeding branch is otherwise unreachable from any sketch — and that is exactly the branch where the two ends of a row used to receive different `y` values, putting POM 1–4 visibly off anchors that still rendered correctly. **APX.16** covers POM 16, whose pair is deliberately NOT one row — the apex points are detected independently and the TD labels them at different heights — so instead of "touches both" it asserts the line favours neither pin: equidistant from both, at exactly half the pair's height spread. See [ADR 0049](docs/decisions/0049-horizontal-span-poms-share-one-row.md). | Chrome CDP |
| `pipeline-tests` | Are the pure stages correct? | Loads `app.js` into a Node VM with DOM stubs and feeds each detection stage a fixed synthetic input; asserts on returned shape and per-stage timing. No Chrome. | Node VM |
| `junction-tests` | Is the junction detector correct? | Drives `detectJunctions` with synthetic masks of known topology (cross = 1 junction + 4 endpoints, L = 1 corner, …) on thin **and** thick strokes (covers Zhang–Suen thinning). No Chrome. | Node VM |
| `learning-tests` | Does the calibration loop behave? | Exercises residual recording / bias via `__braAutoModeDebug.learning`: 5 consistent corrections activate bias; OFF blocks collection; duplicate samples ignored; large residuals rejected; reset clears buckets. | Chrome CDP |
| `evidence-tests` | Does style evidence capture work? | `__braAutoModeDebug.styleEvidence`: empty summary well-formed; add/list(newest-first)/forget; after apply + simulated TD edit, candidates carry normalized coords and commit persists; a TD-deleted POM records confirmed-absent evidence. | Chrome CDP |
| `autosave-check` | Does autosave/restore work? | Injects a state edit, waits for the debounced autosave, reloads, and asserts the restore banner appears and Restore recovers the annotation. | Chrome CDP |
| `curve-polyline-tests` | Do multi-anchor curves keep accurate geometry as their segment count grows? | Loads the real curve/polyline, hit-test, marquee, label, and measurement source parts into a Node VM. Proves straight and zero-anchor curves are byte-identical to the legacy sampler; 1–4 shape-preserving anchors have negligible length drift; a 30-segment S-curve stays within 0.1% of dense arc-length truth while the replaced 2-chord sampler under-counts by more than 75%; the curve bulge remains hittable and marquee-selectable; stitch and half-arc label samples follow dense truth; sampling is zoom-independent and a 100-segment case stays within the 512-evaluations-per-segment structural cap and a generous runtime smoke bound. | Node VM |

Section 8 (US-088) drives a devicePixelRatio change (1 -> 2 -> 1) through CDP and asserts the backing buffer tracks it, because a ResizeObserver is structurally blind to a density change and `resize` fires inconsistently (measured: Chrome emits one going up and none coming back down). Section 7c (US-092) does the same for text notes, with two fixtures on purpose — one written ON the photo, one parked BESIDE it with a leader arrow pointing in — because a note attaches to a sketch in two ways and a box-centre-only rule strands the second, which is the shape a TD writes most often; a control that removes the leader rule fails the outside note while the inside one still passes. Needs `demo/`, so it runs in the private repo only. 225 assertions. Section 4c (US-093 / [ADR 0053](docs/decisions/0053-curved-lines-grow-extra-anchor-points-on-demand.md)) drives the whole curve-anchor design through real gestures on one curved POM: the Add point button appears the instant the curve is selected; clicking it inserts an anchor on the existing path, and that is **three** separate assertions, none of them substitutable for another: the anchor sits < 0.5px off the curve's own drawn path; it sits at the *nearest* point of that path rather than at the nearest sampled vertex (its distance from the click may not exceed the click's own distance from the path by more than 0.5px); and the **drawn path itself** moved < 0.5px, measured as a symmetric Hausdorff distance between the path resampled at 96 chords per Bézier segment either side of the insertion — parameter-independent on purpose, because one cubic becoming two re-parameterizes the curve, so an equal-`t` comparison would report a shape change that is not there and a same-`t` agreement would say nothing about the stretches in between. The click lands at **t = 0.4271, not t = 0.5**: `nearestPointOnCurve` samples this curve into 24 chords, so t = 0.5 is exactly vertex 12/24, the old vertex-nearest search returned it verbatim, and the "no jump" assertion had been passing by coincidence of the fixture rather than by being right. Negative controls, computed on POM 9's real control points at this fixture's zoom, 2026-08-21: correct de Casteljau insertion scores 0.0012px of shape drift and 0.385px of jump; an `insertCurveAnchorAt` that set the new anchor's point and both handles to the click and left `control1`/`control2` alone scores 0.9370 / 0.000 (fails the shape check only); a vertex-snapping search scores 0.0012 / 2.285 (fails the jump check only) — and at t = 0.5 it failed nothing at all. Two guards keep the shape measurement honest rather than merely green: the line must not carry the legacy `midPoint` model, which the harness path sampler deliberately does not reproduce, and one insertion must leave exactly two Bézier segments. The click is also aimed at an **integer screen pixel**, with the harness asked which world point the app therefore received: `MouseEventInit` types `clientX` as a C-style long, so a fractional click is silently rounded by up to 0.33 world px — larger than everything this section is trying to measure. A negative control confirmed the mirror assertion actually fails when the mirroring call is removed (exact message: "must keep the opposite handle collinear"). That is the same 35.5px as the original ADR-0051 bug, reached by an ordinary TD action. The scenario carries its own **height-axis** assertion (the canvas TOP or HEIGHT must change) rather than leaning on the shared vacuousness guard, which a width change alone satisfies and which would therefore let this section drift back to proving one axis while claiming two; plus three guards so it cannot pass against the wrong state — the device-metrics override actually took, what ended up selected is still a curve, and Add point is showing. (In the un-restored post-Apply state, where Undo is visible, the same reflow happens at 1440px too — measured 95.5 → 131.0.) Sections 4d/4e (found by `/code-review` on the US-093 diff, 2026-08-21, then fixed same day): `moveAnnotation` (`src/manual/pointer-events.js`) and `scaleAnnotationAbout` (`src/manual/viewport.js`) both predate `ann.points` and walked a fixed field list that never mentioned it — dragging a curve's body (or the photo it sits on) moved every fixed field but left an interior anchor frozen at its old absolute position, tearing the curve; resizing a photo scaled start/end/control1/control2 but not the anchor, silently changing that POM's measured length. None of the 24 suites already in this repo exercised "move/resize a curve that has an interior anchor," so this shipped through the same US-093 verification pass that reported 94/94 green (the suite's size at that moment, before 4d/4e and before the restored height-axis scenario) — "no suite caught it" and "no bug exists" are not the same claim. 4d drags an unselected curve's body from a point clear of the anchor (shape-preserving insertion means the pre-insertion `bez(before, t)` formula still lands exactly on the curve) and asserts the anchor moves by the same delta as `start`; 4e reuses the resize section's "widest clear spot" technique and asserts the anchor's position relative to `start` scales by the same factor as the photo. A negative control confirmed 4d fails with exactly "must move an interior anchor by the same delta as its endpoints," then the rebuild hash matched the fixed build exactly after reverting. **Sections 4f/4g/4h** (US-093 / ADR 0053 code review, 2026-08-21) close three gaps that each shipped through a run of this file reporting itself green, and each asserts the property rather than the plumbing — "the label moved" and "a handle moved" are both satisfied by the broken behaviour. **4f, handle ARBITRATION:** `hitTestSelectedHandles` returned the first match in declaration order, so a press equidistant between anchor 0's small `handleOut` and anchor 1's emphasized, endpoint-sized `point` bent the handle the TD was not aiming at — and `control1`/`control2`, tested first, shadowed any anchor inserted within `controlRadius` of them, which is exactly the state inserting near an endpoint produces. 4c cannot see this: it presses EXACT handle positions, where the distance is 0 and first-match, nearest-wins and "the bigger painted target always wins" all answer identically. So 4f drags one handle into the other's catch zone to build the crowding a tight curve gives a TD, searches the segment between the two for an integer-pixel press where the shipped rule and a named RIVAL rule disagree, and asserts which handle the press actually opened — read off `getInteraction().part`, not from "something moved", because a mis-arbitrated press moves something either way. Four rows: three against the pre-fix `legacy-first` rule and one against the plausible alternative `point-tier`. Each row also asserts the rival's answer at that pixel, that the runner-up is the rival's pick, and that the press sits near midway between the two, so a geometry drift that makes the rules agree goes red instead of passing on a press that proves nothing. **4g, the POM CALLOUT across 1–4 inserted anchors:** `handleAddPointClick` rewrites `ann.label` from `computeDefaultLabelPosition`, and that function used to pick the middle *entry* of `ann.points` — one anchor 20% along POM 18's armhole curve teleported the number ~95px off mid-curve, permanently, and it then shipped in Copy Image, Export PDF and the Excel embedded PNG. The old rule was non-monotonic in anchor count too (1 and 2 both resolve to `points[0]`, 3 and 4 to `points[1]`), so 4g inserts four anchors in turn and at every count measures the callout against the half-arc-length point of the DRAWN path, sampled at 400 chords per Bézier segment so the reference is the geometry and not a re-run of the code under test. The same geometry is scored against the old rule as a negative control — it must stay more than 10px out, or the row has stopped discriminating — and an insertion must never flip `labelManual`, since a TD-placed label is deliberately left alone. **4h, the Add-point REFUSAL paths:** `handleAddPointClick` (`src/manual/canvas-tools.js`) has **four**. A click farther from the curve than its accept tolerance (toast: "Click on the curve to add a point."). A landing spot the separation gate refuses because the split there would collapse onto geometry the line already has (toast: "Too close to an existing point. Zoom in to place one here.") — that predicate was re-tuned twice during this review, so read it in `handleAddPointClick` rather than trusting a radius quoted anywhere, this document included. An out-of-range segment index back from `insertCurveAnchorAt` (toast: "Could not add a point there."), which no live path can produce today and which exists so that stays a guard instead of an assumption the next caller inherits — the one path 4h does not drive. And a silent `return` when `canAddCurveAnchor` declines: a non-curve, a line hidden by the review × Hide toggle, or a multi-line selection, with an armed Add-point tool falling back to Select. All four are silent-or-toast paths, so a regression that turns one of them into an insertion yields a wrong measurement and no error. 4h drives the miss, the separation refusal, **and** the **nearest legal landing spot**, which must still be ACCEPTED — the refusal half alone would pass on a button that is visible and inert everywhere, which is what the gate's first value actually produced on any short curve. That accepted control is computed in the harness by mirroring `previewCurveAnchorInsertion`'s four de Casteljau lerps, and it asserts BOTH halves of the gate at the spot it aims at — distance to the nearest occupied point, and the shortest handle the split would write — which is strictly stronger than the aim it replaces. That earlier aim, a spot 1.6x the gate from the endpoint, was itself a bug in the test rather than a defect in the product: near an end the binding half is the handle span, about a third of the anchor clearance, so a spot chosen by its distance from the endpoint was still inside the gate and failed against correct code. It proves a refused click leaves the tool armed for the next try and pushes no history entry (one undo has to reach the pre-refusal state), and it covers both withholding cases: for a hidden line the button is withdrawn on the next toolbar sync and pressing it anyway does not enter the tool. The multi-line case carries the blast radius, and 4h measures it rather than quoting the source comment: with a group selected, the Backspace that undoes an insertion is not the anchor-delete branch — `deleteSelected` gates that on a single selection — so it falls through to the GROUP delete, taking 2 lines and filing 2 keys into `state.deletedPomKeys`, which drops those rows from the exported workbook. A fourth habit worth copying: 4f and 4h read the numbers they aim at — `hitTestSelectedHandles`' two catch radii, and `handleAddPointClick`'s accept tolerance and separation gate — out of the served `app.js`, and failing to extract them is itself an assertion. Hard-coded copies are how this exact doc/test drift recurs: a re-tuned gate leaves the probes pressing a spot that is no longer on either side of the boundary, and the suite stays green while testing nothing. **Section 4i** (US-093 / ADR 0053 code review, 2026-08-21) covers an interior anchor on an **UNSELECTED** line, the one press none of the sections above reaches: `hitTestAnyEndpoint` — the test that makes any visible line's end grabbable on the first press (section 1) — was never made anchor-aware, and no insertion gate can keep an anchor away from an end, because a TD can simply DRAG one there. Section 4f case (c) builds exactly that geometry, but there the curve is selected, so `hitTestSelectedHandles` answers and this path never runs. The fix makes an endpoint defer to a strictly closer anchor of the same line, and deferring is not "grab the anchor instead": interior anchors are painted only for the selected line, so the press falls through to the line BODY, selects the line, and the anchor is grabbable on the next press — both halves asserted, along with "nothing moved" and "the measured value held". The counterfactual is what prices the bug, and the suite measures it live through the product rather than asserting a remembered number: with the anchor deleted, the SAME pixel opens a handle drag on that endpoint, moves the landmark pin 22.8 screen px and takes the POM's measured value from 104 to 111 (POM 9 on this fixture, 2026-08-21). It is also the only evidence that pixel is inside the endpoint's catch radius — so the pre-fix rule really did answer `start` there, and without it the deferral assertions could be passing on a press the endpoint never wanted. **Known limitation (4g):** one of its three assertions is deliberately loose. The callout is allowed to move by exactly the 14.573 screen px collision nudge that `nudgeAutoLabelsToAvoidCollisions` applied at Apply and that the insert path discards, "and nothing more", because the strict form (`movedFromBasePx < 1.5`) is false against the current product: every `computeDefaultLabelPosition` caller that runs after a geometry edit loses that nudge, not just this one, so an insertion can drop a POM number back on top of a neighbour's. That is a known, tracked product defect rather than slack in the test — the round-1 teleport reads 71.8px against a 14.57px nudge and still goes red — and the suite comment says to tighten this to the strict form once the nudge is preserved. | Chrome CDP |

## Stability vs. correctness (important distinction)

- **`golden` = stable.** It compares against the tool's *own* previous output.
  Green means "nothing changed," which can be a *stable wrong answer*.
- **`accuracy` = correct.** It compares against a *human's* corrected anchors.
  This is the only suite that can say the detector is actually right.

So a detection change that lowers `accuracy` error but trips `golden` is a
**good** change — verify with `accuracy`, then re-baseline `golden --update`.
Never re-baseline golden to silence a regression you haven't checked against
accuracy or invariants.

Since the accuracy regression gate landed, "verify with `accuracy`" is
mechanical: `npm run accuracy` exits non-zero when correctness got worse than
the committed baseline, and prints the ratchet hint when it got better. The
two `--update` flags are deliberate mirrors — `golden --update` re-seeds
*stability*, `accuracy --update` re-seeds *correctness*, and the second should
generally be run (and its diff reviewed) before the first.

## Ground truth (for `accuracy`)

Produced by the in-app labeling flow: open `index.html?label=1`, add the image,
Detect Sketch, drag every anchor onto the true landmark, click **Save Ground
Truth**, and drop the file in `scripts/groundtruth/<image-basename>.json`.
Growing this corpus beyond the demo set is milestone **M3** in the charter and
the prerequisite for calibrating the tolerance bands (**M4**).
