# Testing — Bra Auto Measure

The suites answer four different questions: **does it build**, **does it run**,
**is it correct**, and **did it change**. Knowing which question a suite answers
tells you when to run it. All commands are `npm run <name>` and live in
`scripts/`.

---

## Quick guide: what to run when

- **After any `src/` edit:** `build` → `check` → `smoke`.
- **After a detection / anchor change:** add `invariants`, `contract`, and
  `golden` (re-baseline with `golden --update` only when the change is
  intentionally better, confirmed by `accuracy`).
- **After a learning / meaning / evidence change:** the matching subsystem suite.
- **Before shipping:** the full set.

`check`, `pipeline-tests`, `junction-tests`, and `export-hidden` need no browser.
The rest drive a headless Chrome over raw CDP (zero npm deps); `accuracy`
additionally needs labelled ground truth and a local Chrome install.

## The suites

| Command | Question it answers | What it does | Runner |
|---|---|---|---|
| `check` | Does it build & wire? | Asserts the committed `app.js` matches what `src/` would build (read-only freshness gate), parse-validates every `src/` part in isolation plus the standalone `opencv_*` / `potrace` / script files, checks every `src/**/*.js` is registered in `source-parts.mjs`, validates the rule JSON contract, and runs the two **shared-scope** gates: no name declared at top level in two parts (the later one silently wins for every caller), and no load-time read of a `const`/`let`/`class` declared in a later part (those do not hoist, so it throws a TDZ `ReferenceError`). | Node, parse-only |
| `smoke` | Does it run end to end? | Headless Auto Mode run on `demo/demo1.jpg`; asserts the pipeline completes and the output is structurally sound. | Chrome CDP |
| `golden` | **Did output change?** (stability) | Runs detection on **every** `demo/*.jpg` and diffs anchors (by kind), draft count, per-POM **draft-line geometry** (start/end/control points, normalized to the source image — guards the fixture→draft path that anchor drift can't see), and `detection.quality` against committed per-image baselines. Fails on drift. `--update` re-seeds baselines; `GOLDEN_TOL` overrides tolerance. | Chrome CDP |
| `accuracy` | **Is it correct?** | Scores detector seeds against **human-placed TD ground truth** in `scripts/groundtruth/`. Lower is better. Bands: tight ≈0.02 ("a TD wouldn't touch it"), loose ≈0.04 ("a nudge fixes it"), normalized image units. Pins the deterministic offline detector for reproducibility. **Regression gate:** every full run is also compared against the committed `scripts/groundtruth/accuracy-baseline.json`; if any labeled image's mean/max error, any anchor kind's mean error, the overall mean, or the count of unseeded ground-truth anchors gets worse (beyond small epsilons — `ACCURACY_GATE_MEAN_EPS`/`_MAX_EPS`/`_KIND_EPS`), the suite exits non-zero. Improvements pass; ratchet them in with `accuracy --update`. **Stale-read guard:** Chrome's cache is disabled and, before every detection, the served `app.js` is SHA-256-verified against disk (re-navigates until fresh) — on this Drive checkout the first read after file churn can silently serve an old build, which shows up as the fragile cradle anchors going missing; images whose ground-truth anchors still go unseeded are re-detected once more. `--only` skips the gate (partial corpus). **Multi-photo boards:** a ground-truth file may name its own image with `imagePath` (so boards in a `demo/` subfolder are discovered at all — the directory scan is not recursive) and declare a `board.aux` list, which is loaded as extra board photos so the TD's real two-photo board is reproduced instead of the primary alone. Single-image fixtures are unaffected. | Chrome CDP + ground truth |
| `measurement-accuracy` | **Are the measured POM *values* correct?** | Value-level mirror of `accuracy` (which scores anchor *positions*). Scores each POM's measured value (inches) against per-POM TD ground truth in `scripts/groundtruth/measurements/<image>.json`, with the same one-sided gate vs `scripts/groundtruth/measurement-accuracy-baseline.json` (epsilons `MEASURE_GATE_MEAN_EPS`/`_MAX_EPS`/`_POM_EPS`). **Non-blocking until Mode B ships:** only `source: td_confirmed` GT is gated (`draft_pending_td` is report-only), and scoring needs a measured-value source (`--measured <file>`) that Stage 1 wires from the measurement engine. Prove the gate math offline with `measurement-accuracy-selftest`. Part of US-039 (Mode B Stage 0). **Roll-out (US-041):** `measurement-accuracy --measured=<run> --promote` recommends the per-POM `MODE_B_ENABLED_POMS` set (only td_confirmed POMs whose fused value beats library-only); `mode-b-readiness` prints, with no ground truth, which POMs produce a coherent measured value across the demo fixtures (where to label GT first). | Node |
| `invariants` | Are structural properties intact? | Checks properties that must hold with no ground truth: geometry (A1–A6), cup bounds (B1–B4), visibility (D1–D3) and shared rows (E1–E4), across all demos. **E1–E3** guard the row model behind the force-levelled horizontal spans: `band-left`/`band-right`, `chest-left`/`chest-right` and `back-strap-left`/`back-strap-right` are each the two ends of ONE row, so they must share a `y` exactly — POM 1 / 3 / 15 draw level at the LEFT end's `y` and silently miss the right pin by any gap. **E4** ties POM 16's drawability to the apex pair's slant: the detector repairs a straddled pair by re-searching the outlier side (US-084) and the drafter demotes past the same 0.06 limit (US-083), so the two numbers live in two files and E4 is what catches them drifting apart. Complements `golden` (change) and `accuracy` (correctness). | Chrome CDP |
| `contract` | Are the fragile POMs semantically right? | Semantic checks (aligned to the POM contract in `POMS_CONTRACT.md`) for the 6 hard front-view POMs — 6, 7, 8 (cradle/cup heights), 9, 10 (inner cup), 16 (apex) — on every demo. Also carries four cross-cutting series: **CLA** (each drafted endpoint sits on its anchor, recomputing the drafter's own formula), **HLN** (the horizontal spans are drawn level), **TRA** (POM 1 / 3 / 15's line passes within `EPS_LINE_ANCHOR` of BOTH required anchors — the property CLA cannot check, because for a force-levelled span CLA reproduces the very `y`-discard that can throw the line off its right-hand pin), **RPF**, and **APX**. **RPF** re-seeds anchors from the captured detection with one side's band/chest ink fields nulled: every fixture in the corpus detects ink on BOTH sides, so the one-sided seeding branch is otherwise unreachable from any sketch — and that is exactly the branch where the two ends of a row used to receive different `y` values, putting POM 1–4 visibly off anchors that still rendered correctly. **APX.16** covers POM 16, whose pair is deliberately NOT one row — the apex points are detected independently and the TD labels them at different heights — so instead of "touches both" it asserts the line favours neither pin: equidistant from both, at exactly half the pair's height spread. See [ADR 0049](docs/decisions/0049-horizontal-span-poms-share-one-row.md). | Chrome CDP |
| `pipeline-tests` | Are the pure stages correct? | Loads `app.js` into a Node VM with DOM stubs and feeds each detection stage a fixed synthetic input; asserts on returned shape and per-stage timing. No Chrome. | Node VM |
| `junction-tests` | Is the junction detector correct? | Drives `detectJunctions` with synthetic masks of known topology (cross = 1 junction + 4 endpoints, L = 1 corner, …) on thin **and** thick strokes (covers Zhang–Suen thinning). No Chrome. | Node VM |
| `learning-tests` | Does the calibration loop behave? | Exercises residual recording / bias via `__braAutoModeDebug.learning`: 5 consistent corrections activate bias; OFF blocks collection; duplicate samples ignored; large residuals rejected; reset clears buckets. | Chrome CDP |
| `evidence-tests` | Does style evidence capture work? | `__braAutoModeDebug.styleEvidence`: empty summary well-formed; add/list(newest-first)/forget; after apply + simulated TD edit, candidates carry normalized coords and commit persists; a TD-deleted POM records confirmed-absent evidence. | Chrome CDP |
| `autosave-check` | Does autosave/restore work? | Injects a state edit, waits for the debounced autosave, reloads, and asserts the restore banner appears and Restore recovers the annotation. | Chrome CDP |
| `board-toolbar-check` | Is the Board toolbar minimal, contextual, accessible, and responsive? | Covers empty/ready/generated Auto states, Manual drawing and selection contexts, primary-action limits, menu focus/arrow/Escape/ARIA behavior, unchanged command endpoints, and layouts at 1440/1024/768 px with no page overflow. The four `*-limitations` suites share their headless machinery — the DOM stub,
rule-fixture loader, VM pipeline load, ink-canvas builder, staged
detect→seed→fixture run, and the `PASS`/`FAIL`/`LIMITATION` reporter — from
`scripts/lib/synthetic-detection.mjs`. A suite only owns its synthetic
mask-builders and its `cases[]`. Each case declares either `hardExpected`
(asserted; a mismatch is a `FAIL` and exits non-zero) **or** `knownLimitation`
(printed as `LIMITATION`, always non-fatal) — so a suite never bakes in an
expectation for behavior that is a known weak spot rather than a contract.

## Stability vs. correctness (important distinction)

- **`golden` = stable.** It compares against the tool's *own* previous output.
  Green means "nothing changed," which can be a *stable wrong answer*.
- **`accuracy` = correct.** It compares against a *human's* corrected anchors.
  This is the only suite that can say the detector is actually right.

So a detection change that lowers `accuracy` error but trips `golden` is a
**good** change — verify with `accuracy`, then re-baseline `golden --update`.
Never re-baseline golden to silence a regression you haven't checked against
accuracy or invariants.

Since the accuracy regression gate landed, "verify with `accuracy`" is
mechanical: `npm run accuracy` exits non-zero when correctness got worse than
the committed baseline, and prints the ratchet hint when it got better. The
two `--update` flags are deliberate mirrors — `golden --update` re-seeds
*stability*, `accuracy --update` re-seeds *correctness*, and the second should
generally be run (and its diff reviewed) before the first.

## Ground truth (for `accuracy`)

Produced by the in-app labeling flow: open `index.html?label=1`, add the image,
Detect Sketch, drag every anchor onto the true landmark, click **Save Ground
Truth**, and drop the file in `scripts/groundtruth/<image-basename>.json`.
Growing this corpus beyond the demo set is milestone **M3** in the charter and
the prerequisite for calibrating the tolerance bands (**M4**).
