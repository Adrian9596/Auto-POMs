# Front End — background, fixed surfaces, improvement backlog

_What the front end is, which parts are contracts we deliberately do NOT
touch, and where the known UX gaps are. For the full project map see
[`../ARCHITECTURE.md`](../ARCHITECTURE.md); for why the tool exists see
[`../PROJECT_CHARTER.md`](../PROJECT_CHARTER.md)._

Last reviewed: 2026-08-18 (after US-082 contextual Board toolbar). The
original improvement backlog is fully worked; new items should come from
TD usage.

---

## 1. Background — how the front end is built

- **One page, no framework.** `index.html` carries layout + CSS;
  `app.js` (generated from the ordered `src/` parts sharing one IIFE scope) carries
  all logic. There is no bundler, no virtual DOM, no component library.
- **Two render surfaces.**
  - The **board** is a single `<canvas>`: images, POM lines, anchors, drafts,
    handles, labels all draw in world coordinates through
    `src/render/render-loop.js` with zoom/pan applied per frame. All sizes
    that must stay constant on screen divide by `state.zoom`.
  - Everything else — toolbar, status bar, Measurements panel, dialogs,
    toasts — is plain DOM, rebuilt coarsely: `updateUI()` re-toggles the
    toolbar and calls `renderSpecPanel()`, which rebuilds the whole table.
- **One interaction grammar.** Click selects (single selection, funneled
  through `setSelection`), drag moves, handles resize, and since US-027 the
  keyboard mirrors the mouse: arrows nudge the selected anchor (Auto) or
  line/point (Manual), Tab cycles the active point. Every gesture — a drag
  or a burst of keypresses (700 ms debounce) — commits exactly **one**
  history entry, so one Cmd/Ctrl+Z undoes one gesture.
- **Feedback channels** are the status bar (persistent hint for the current
  tool/selection), toasts (transient, single slot), and the Help dialog
  (shortcut reference). New UI should reuse these, not invent new ones.
- **Modes.** Fresh load boots Auto Mode; "Apply Lines" hands off to Manual
  Mode for TD correction (decision
  [`decisions/0008-reenable-manual-mode.md`](decisions/0008-reenable-manual-mode.md)).
  Manual-only controls hide under `body.app-auto` via the `.manual-only`
  CSS class in `index.html`.
- **Contextual Board toolbar.** The Board has one primary action for the
  current state. Auto follows Add image → Detect → Generate; Manual keeps
  drawing tools direct, reveals selection actions only when applicable, and
  groups secondary commands under Arrow, Color, File, Export, and More menus.
  `src/ui/board-toolbar.js` owns visibility and keyboard menu behavior; the
  existing command element ids remain the action endpoints.
- **Offline by design.** No network call ever carries sketch or measurement
  data; exports (Copy Image, PDF, Excel) are generated client-side.

## 2. What we don't touch (fixed contracts)

These are load-bearing. Changing them is possible but goes through a story /
decision, never as a side effect of front-end polish.

| Surface | Contract | Why |
| --- | --- | --- |
| `app.js` | Never edited directly — generated by `npm run build` from `src/*` (order in `scripts/source-parts.mjs`) | Hand edits are silently overwritten |
| The 18 POMs + anchor schema | `auto_mode_rules/*.json`, versioned in `version.json` | Spec-sheet contract with TDs; JSON wins over prose |
| Placement views | Every POM renders on exactly one view (`front_outer` / `front_inner` / `back`); POM 14 is the `front_to_back` exception | Review/apply logic and exports assume it |
| Mode behaviour | Auto-first boot, unconditional Manual handoff after Apply, visible toggle, applied projects reopen in Manual | Decision 0008; smoke + meaning-tests assert it |
| Determinism | Same sketch → same lines (`npm run golden`); front-end changes must not perturb detection | TD trust + regression gate |
| Test hooks | `window.__braAutoModeDebug` stays exposed | Every headless suite drives the app through it |
| Coordinate spaces | Anchors normalized `[0,1]` in source-image px; annotations in world px; eraser strokes in image-local px | Persistence, learning, and exports all assume them |
| One-commit-per-gesture history | Drag or key burst = one snapshot; fingerprint-based dedupe | Undo semantics TDs rely on |
| The keyboard map | S/0/C/X/L/F/N/H/A/G/E/R/D, arrows, Tab, Esc, Space, Cmd+C/V/Z, `[`/`]` are all claimed (see Help dialog) | Rebinding needs TD sign-off — precedent: eraser moved E→X on TD request 2026-07-10 |
| Learning boundary | UI only *feeds* samples (drag/nudge residuals); learning never mutates rule JSON, stays optional/resettable | Charter invariant |

## 3. What needs improvement (known gaps, roughly prioritized)

1. ~~**Measured value is not live during adjustment.**~~ **Done (US-028,
   2026-07-15):** the Value cell (and its tolerance chip) now refreshes per
   keystroke / mousemove via `refreshMeasuredValueForAnnotation` — a
   targeted cell replace, no full panel rebuild, no focus theft.
2. ~~**No on-canvas readout.**~~ **Done (US-029, 2026-07-15):** a floating
   pill next to the moving point shows the live value plus the Δ ✓/✗
   verdict while dragging or nudging (`drawAdjustmentReadout`,
   render-annotations); it shares `specDeltaText` with the panel chip so
   the two can never disagree, and disappears on gesture commit.
3. ~~**Tab ring skips curve bend handles.**~~ **Done (US-030, 2026-07-15):**
   the ring now continues past the main points into the bend handles
   (start bend → mid bends → end bend), built dynamically from the parts
   the curve actually has. Curves are fully keyboard-tunable.
4. **Tab is captured while a line is selected**, so keyboard-only travel
   from canvas to panel fields requires Escape first. Standard for canvas
   tools, but undocumented outside the Help dialog.
5. ~~**Full-table spec panel rebuilds.**~~ **Done (US-033, 2026-07-15):**
   `renderSpecPanel()` skips the rebuild when its data fingerprint is
   unchanged (selection-only clicks → highlight update, 0.21 ms vs 12.65 ms
   at 72 rows). **Maintenance rule:** a new panel feature that renders from
   state not yet fingerprinted must add its input to
   `specPanelFingerprint()` in `src/ui/spec-panel.js`, or the panel will go
   stale — the function carries the same warning in a comment.
6. ~~**Size L / TOL fields are plain text.**~~ **Fully done** — stepping
   (US-031) plus unit hinting + validation (US-035, 2026-07-15): headers
   show the active unit ("(in)"/"(cm)"), tooltips name each field's unit
   and role, `parseSpecNumber` accepts fractions (`12 1/2`) everywhere it
   is used (chip, readout, stepping, size run, Excel L2), and unparseable
   values get a visible red invalid state instead of silent ignoring.
7. ~~**Single toast slot.**~~ **Done (US-032, 2026-07-15):** colliding
   toasts now queue (bounded to 3, ~0.9 s reading window, duplicates
   coalesce) instead of overwriting. Status-style toasts (Tab cycling,
   brush size) pass `{ replace: true }` — latest wins there by design, so
   stale states never replay after a keyboard burst. New toast call sites
   should choose: event message → default (queued); live status →
   `replace`.
8. **Accessibility debt — cheap wins done (US-034, 2026-07-15):** toasts
   are `role="status" aria-live="polite"` (the keyboard-workflow narration
   is announced), all buttons show a `:focus-visible` outline, and the
   active handle is a bullseye (fill + detached outer ring — a shape cue,
   not just color). Still out of scope: full screen-reader support for the
   canvas board itself (no ARIA reflection of line geometry/selection
   state), which is acceptable for a sighted-TD desktop tool.
9. ~~**Desktop-only assumptions.**~~ **Touch layer done (US-036,
   2026-07-16):** one finger = the mouse (select / drag / draw / erase),
   two fingers = pinch zoom + pan, double-tap = fit; routed through the
   existing mouse handlers via a `pointerType`-filtered pointer-event
   layer, so gesture semantics (one history commit per gesture) are
   shared, not duplicated. Canvas is `touch-action: none`; panel keeps
   native scrolling. **Owed:** a hands-on pass on a physical touch device
   — verified with synthetic PointerEvents only. Keyboard-only features
   (arrow nudge, Tab ring) still need an external keyboard on tablets.

## 4. How to work on the front end

1. Find the part via the module map in [`../ARCHITECTURE.md`](../ARCHITECTURE.md)
   (interaction logic: `src/manual/interactions.js`; canvas drawing:
   `src/render/*`; panel/dialogs: `src/ui/*`; mode/status chrome:
   `src/manual-tools.js`).
2. Edit `src/*`, then `npm run build` → `npm run check` → the suite covering
   what you touched ([`../TESTING.md`](../TESTING.md)); `npm run golden` +
   `npm run smoke` whenever behaviour near the pipeline or modes moved.
3. New shortcuts or visible behaviour: update the Help dialog
   (`src/ui/dialogs/help-dialog.js`) and the status-bar hint
   (`src/manual-tools.js`) in the same change, and verify hands-on in the
   browser preview — CDP `computer` key presses may not map to `e.key`
   values (send real `KeyboardEvent`s from `javascript_tool`).
